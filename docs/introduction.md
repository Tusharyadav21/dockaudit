# Why We Built Dockaudit

If you've been a developer or a DevOps engineer for a while, you probably know the feeling. You run `docker system df` or notice your laptop's hard drive is completely full. You see that Docker is eating up 60GB of disk space. 

So what do you do? You usually run something like `docker system prune -a`. 

But here's the catch: that command is terrifying. It deletes *everything* that isn't currently running. What if it deletes the database volume for that client project you haven't spun up in a month? What if it wipes out the 20GB build cache that you *actually* need to avoid a 45-minute re-compilation tomorrow morning? 

The problem with Docker's built-in pruning tools is that they lack **context**. They treat your environment as a flat list of items, rather than an interconnected web of projects, volumes, and networks.

That's why we built **Dockaudit**.

## The Real Problem: Context and Confidence

Most developers accumulate years of Docker resources:
- Dozens of abandoned containers.
- Huge orphaned volumes full of stale data.
- Unused networks from old experiments.
- Massive build caches generated by Docker Desktop or VS Code Dev Containers.

When you look at this mess, existing tools just give you a raw data dump. They tell you that a volume is 8GB. But they don't answer the human questions:
- *Why does this exist?*
- *What created it?*
- *If I delete it, what breaks?*

## Our Solution

Dockaudit is designed to bring confidence back to cleaning up your infrastructure. It is not just another wrapper around `docker rm`. 

Instead of looking at your resources individually, Dockaudit builds a **Dependency Graph** of your entire Docker daemon. It looks at how your `docker-compose.yml` projects relate to your networks, which containers birthed which volumes, and what images rely on what.

### The Human Use Cases

1. **"I just need to free up some space, fast."**
   You run `dockaudit doctor`. It instantly analyzes your environment and tells you precisely how much "safe" space you can recover (e.g., dangling images and entirely orphaned volumes) without breaking any existing projects.

2. **"Wait, what is this random 14GB volume?"**
   You run `dockaudit explain volume my_weird_volume`. Dockaudit traverses the dependency graph and tells you exactly what it is. "Oh, this was created by the `billing-api` compose project 3 months ago, and it's currently attached to a stopped postgres container." Now you have the context to decide if you want to keep it.

3. **"Clean up the junk, but don't break my stuff."**
   You run `dockaudit plan`. Dockaudit generates a categorized list of deletions. Anything marked `SAFE` is mathematically proven (via graph traversal) to have no dependencies. Anything marked `DANGEROUS` is actively being used. Then, `dockaudit clean` walks you through deleting the junk interactively.

4. **"Is our CI/CD runner bloated?"**
   You drop `dockaudit doctor --ci` into your GitHub Actions pipeline. It spits out a clean JSON payload warning your team if the runner is accumulating too much cache or too many orphaned volumes over time.

## Privacy First

We built this for engineers, which means we built it to be completely local. Dockaudit never connects to the internet, never sends telemetry, and only speaks directly to your local Docker socket. 

It’s just you, your daemon, and finally, a bit of clarity.
